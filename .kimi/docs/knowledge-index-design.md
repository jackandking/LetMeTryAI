> 版本: v1.0
> 作者: Evolution Agent
> 日期: 2026-04-23
> 状态: 设计文档（待审阅）

## 1. 背景与动机

### 1.1 问题场景

2026-04-23，用户询问"womanai 为什么 0 采用"。Agent 直接读取了 dev 目录的数据（断档在 4/12），得出错误结论：

- ❌ 错误结论: "womanai 近7天 0 采用"
- ✅ 真实数据: prod 目录显示 womanai 每天都有 3-17 个新达人挂载（近7天共 56 个）
- ✅ 真正问题: 新发布的任务当天 0 被采用，达人持续挂载历史旧任务

**根因**: Agent 没有先验证数据采集链路（prod vs dev、时效性、指标口径），直接读数下结论。

### 1.2 现有架构的缺陷

当前 LetMeTryAI 的知识管理体系：

| 文件 | 用途 | 自动加载 | 问题 |
|------|------|---------|------|
| `SESSION_MEMORY.md` | Session 上下文 | ✅ | 不断追加，会膨胀 |
| `EVOLUTION_STATE.md` | 指标看板 | ✅ | 只存数字，不存经验教训 |
| `.learnings/LEARNINGS.md` | 长期知识库 | ❌ | 写了但新 session "看不见" |

**矛盾**：
- LEARNINGS 适合存详细的最佳实践，但新 session 不自动加载 → 知识"沉睡"
- SESSION_MEMORY 自动加载，但存全文会快速膨胀 → 上下文被污染
- 全部加载（把 LEARNINGS 加入自动加载列表）→ 上下文超限

### 1.3 需求

设计一种机制，让 Agent：
1. 启动时只加载**轻量索引**（固定大小，不膨胀）
2. 执行任务时，**按需加载**与当前任务相关的学习点
3. 学习点来源不限于 LEARNINGS.md，可以是任何文件
4. 加载过程对 Agent 透明（自动触发，不需要用户手动指定）

---

## 2. 设计目标

| 目标 | 描述 | 验收标准 |
|------|------|---------|
| **G1: 上下文精简** | 新 session 启动时不加载任何 learning 全文 | 启动时额外 token < 500 |
| **G2: 按需精准** | 只加载与当前任务相关的学习点 | 无关学习点绝不加载 |
| **G3: 可扩展** | 支持任意数量的学习文件 | 索引表可以无限增长 |
| **G4: 透明触发** | Agent 不需要手动选择加载哪条 | 关键词匹配自动触发 |
| **G5: 历史可查** | 所有学习点有来源、有时间戳、有场景 | 可追溯、可审计 |

## 3. 架构设计

### 3.1 核心概念

```
┌─────────────────────────────────────────────────────────────┐
│                     Session 启动时                           │
│  1. 读取 SESSION_MEMORY.md（含 Knowledge Index 索引表）      │
│  2. 读取 EVOLUTION_STATE.md                                  │
│  3. 读取 AGENTS.md                                           │
│                                                              │
│  → 此时 learning 全文均未加载                                │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼ 用户输入 / 任务触发
┌─────────────────────────────────────────────────────────────┐
│                     关键词匹配阶段                           │
│  扫描用户输入 + 当前任务上下文                               │
│  与 Knowledge Index 中的 `触发关键词` 做匹配                 │
│                                                              │
│  匹配到 → 进入加载阶段                                       │
│  未匹配 → 正常执行，不加载任何 learning                      │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼ 匹配成功
┌─────────────────────────────────────────────────────────────┐
│                     按需加载阶段                             │
│  1. 读取 `来源文件` 的指定 `行号范围`                        │
│  2. 将内容注入当前上下文（作为 system prompt 补充）           │
│  3. 继续执行用户任务                                         │
│                                                              │
│  → 此时 Agent "记得"了这个学习点                             │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 数据格式

#### 3.2.1 Knowledge Index 表（存于 SESSION_MEMORY.md）

```markdown
## 知识索引 (Knowledge Index)

> 轻量索引表，新 session 启动时自动加载。
> 用到哪条，自动加载哪条。不要手动读取全文。

| 触发关键词 | 来源文件 | 行号范围 | 摘要 | 记录日期 |
|-----------|---------|---------|------|---------|
| 调研,数据源,数据验证,prod,dev | `.learnings/LEARNINGS.md` | L112-L130 | 调研前必须先验证数据采集链路和指标口径 | 2026-04-23 |
| 进化,evolve,auto-run,auto-evolve | `.kimi/EVOLUTION_STATE.md` | 全文 | 进化引擎指标看板和历史行动 | 2026-04-23 |
| womanai,女人爱,新任务采用 | `.learnings/LEARNINGS.md` | L131-L150 | WomanAI 新任务采用率低分析 | 2026-04-23 |
```

**字段说明：**

| 字段 | 必填 | 格式 | 说明 |
|------|------|------|------|
| `触发关键词` | 是 | 逗号分隔 | 用户输入匹配到任意一个词即触发加载 |
| `来源文件` | 是 | 相对路径 | 从项目根目录开始的路径 |
| `行号范围` | 是 | `L{start}-L{end}` 或 `全文` | 精确定位，避免加载无关内容 |
| `摘要` | 是 | 一句话 | 让人快速判断这条是否相关 |
| `记录日期` | 是 | ISO 日期 | 用于追溯和过期清理 |

#### 3.2.2 Learning 条目格式（存于 .learnings/LEARNINGS.md）

```markdown
## {YYYY-MM-DD} — {标题}

**场景**: {什么情况下会用到这条学习}

**错误**:
- {具体做了什么错事}
- {导致了什么后果}

**正确做法**:
1. {步骤1}
2. {步骤2}
3. {步骤3}

**关键区分**:
- {术语A}: {定义}
- {术语B}: {定义}

**教训**: {一句话总结}
```

**锚点标记**：每条 learning 之间用 `---` 分隔，方便行号定位。

## 4. 加载触发机制

### 4.1 触发时机

| 时机 | 是否触发 | 说明 |
|------|---------|------|
| Session 初始化 | ❌ 否 | 只加载索引表，不加载 learning 全文 |
| 用户发送消息 | ✅ 是 | 扫描用户输入，匹配关键词 |
| Agent 执行子任务 | ✅ 是 | 扫描子任务描述，匹配关键词 |
| 加载后再次匹配 | ❌ 否 | 避免循环加载（已加载的不再重复加载） |

### 4.2 匹配算法

```python
def should_load_learning(user_input, task_context, index_entry):
    """
    判断是否需要加载某条 learning
    """
    keywords = index_entry['触发关键词'].split(',')
    
    # 合并所有文本来源
    text_to_scan = (user_input + ' ' + task_context).lower()
    
    # 任意关键词匹配即触发
    for kw in keywords:
        if kw.strip().lower() in text_to_scan:
            return True
    
    return False
```

**匹配示例：**

| 用户输入 | 匹配到的关键词 | 加载的学习点 |
|---------|--------------|------------|
| "分析一下 womanai 的数据" | `womanai` | WomanAI 新任务采用率低分析 |
| "调研一下最近的采用率" | `调研` | 调研前必须先验证数据源 |
| "auto-evolve 的数据对不对" | `auto-evolve`, `数据` | 进化引擎指标 + 数据源验证 |
| "帮我写一个投票小程序" | （无匹配） | 不加载任何 learning |

### 4.3 去重机制

每条 learning 加载后，在 session 上下文中标记为 `loaded`，同一 session 内不重复加载。

### 5.2 evolution-engine skill 规则更新

在 skill 的"承上启下机制"部分增加第 5 步：

```markdown
**每次启动时，按顺序读取以下文件加载上下文：**

1. `SESSION_MEMORY.md` — 当前项目状态、关键决策、待办
2. `EVOLUTION_STATE.md` — 进化引擎状态、指标、历史行动
3. `AGENTS.md` — 项目全局规范
4. `.harness/AGENTS.md` — Harness 子系统规范
5. **【新增】SESSION_MEMORY.md 中的 `## 知识索引` 表** — 轻量索引，不加载全文

**执行用户任务前，检查是否需要按需加载：**

- 扫描用户输入和任务上下文
- 与知识索引中的 `触发关键词` 匹配
- 匹配成功 → 读取 `来源文件` 的 `行号范围`，注入上下文
- 匹配失败 → 正常执行，不加载
```

### 5.3 与 auto-evolve 的集成

auto-evolve 引擎在执行分析任务时，也应触发知识索引加载：

- 分析" Harness 失败率" → 加载所有与 Harness、失败率相关的 learning
- 分析" womanai 采用" → 加载 womanai 相关的 learning

这样 auto-evolve 也能从历史错误中学习，避免重复犯错。

## 7. 风险与回退方案

| 风险 | 影响 | 缓解措施 | 回退方案 |
|------|------|---------|---------|
| 关键词匹配过于宽泛 | 加载无关 learning，污染上下文 | 关键词尽量精确（3-5 个词） | 手动调整关键词 |
| 关键词匹配过于严格 | 该加载的没加载 | 定期 review 匹配日志 | 增加同义词 |
| 行号范围漂移 | 加载到错误内容 | learning 条目之间加 `---` 锚点 | 用文本搜索代替行号 |
| 索引表膨胀 | 启动加载变慢 | 索引表只存元数据，每条约 150 字符 | 按日期归档旧索引 |
| 多文件冲突 | 同一条 learning 存在多个版本 | 来源文件路径唯一 | 以最新日期为准 |

## 9. 附录：参考案例

### 案例 1: 调研前先确认数据源（本文档的直接动机）

**触发关键词**: `调研,数据源,数据验证,prod,dev,指标口径`

**来源**: `.learnings/LEARNINGS.md` L112-L130

**摘要**: 任何业务指标调研，第一步永远是验证数据采集链路（目录、时效性、指标口径），而不是直接读数。

**场景**: 用户要求分析某个品牌的达人采用率时，Agent 容易直接读取 dev 目录的过期数据。

**正确做法**:
1. `crontab -l` 确认任务运行在哪个目录（prod vs dev）
2. `ls -lt daily-runs/` 确认数据采集是否正常
3. 明确指标口径（fetched ≠ 新任务采用，queueAdded ≠ 达人采用）
4. 再下结论

**关键区分**:
- `fetched`: 平台上有多少达人视频挂载了该品牌（含历史，非新采用）
- `queueAdded`: 加入 follow 队列的达人（我们主动关注，非达人采用）
- **新任务采用**: 需要看具体视频挂载到了哪个任务路径

**教训**: 数据不会说谎，但读错数据源会让 Agent 说谎。
